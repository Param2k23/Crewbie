# Decisions

| Date | Requirement | Decision |
|---|---|---|
| 2026-10-25 | I-01 (07 Phase 0) | `crewbie-v2` is cut from the latest `origin/master` (fast-forwarded to f7635ef, which already contains `integration/crewbie` via PR #6). That state is what moves into `legacy/`. The owner is the only committer for now. |
| 2026-10-25 | 07 Phase 0, task 6 | The old `.env.example` is replaced. Its only still-used variable, `NEXT_PUBLIC_CREWBIE_API_URL` (read by `apps/web`), is kept as a commented line at the bottom of the new file. |
| 2026-10-25 | 09 section 5 | Dependency age rule is enforced with `exclude-newer = "2026-10-11T00:00:00Z"` in `[tool.uv]` (14 days before today). Move the date forward when new packages are needed. |
| 2026-10-25 | SRS 5.3 | "Ties go to the vibe of the earliest member" is implemented as: among the tied vibes, pick the vibe held by the earliest-joined member (ties on join time broken by alias). Otherwise a member holding a non-tied vibe would decide the result. |
| 2026-10-25 | SRS 5.3 | `RoomState.window` is `None` when members' effective windows share no time (or there are no members). Callers must not offer a join that would produce this; the matcher enforces it in Phase 3. |
| 2026-10-25 | 07 Phase 1, task 2 | In `CREWBIE_ENV=dev` with no `CREWBIE_ENVELOPE_KEY`, a key is generated once and stored at `data/dev_envelope.key` (mode 0600, git-ignored) so envelopes survive restarts. Prod requires the variable. |
| 2026-10-25 | FR-OFR-01, 5.2 | `budget_cap_usd` is stored as a float inside the encrypted envelope. Money amounts here are only compared, never summed, so float is acceptable. |
| 2026-10-25 | NFR-REL-01 | "Backoff 1, 2, 4, 8, 16 s; then marked failed" is implemented as 5 retries after the first failure (6 attempts in total). |
| 2026-10-25 | 02 section 3 | `rooms.version` starts at 1 and every `apply_state` that follows a join, leave or agreement bumps it. Offers store the version they were computed against. |
| 2026-10-25 | 09 section 1 | `api` sits above `discord_bot` and `workers` in the import-linter layers. `api/app.py` is the composition root that starts them in its lifespan (02 section 1), so it must import them. They remain independent of each other. |
| 2026-10-25 | 02 section 5 | Intent state machine gains `matching -> withdrawn` and `offered -> withdrawn`. FR-INT-06 and FR-INT-03 (replace an unjoined intent) need a student to leave before joining. |
| 2026-10-25 | 03 section 1 | New error codes outside the contract table: `FORBIDDEN` (403, seeding in prod), and bot-only `LINK_CODE_INVALID` (reason expired/used/unknown) and `LINK_CONFLICT` (reason discord_user_linked/install_linked; the bot confirms and retries with `replace=True`). |
| 2026-10-25 | NFR-SEC-04 | Admin endpoints return 404 when `CREWBIE_ADMIN_TOKEN` is unset, 401 for a missing or wrong token. |
| 2026-10-25 | 06 section 1 | `crew.py accept` prints `THREAD none` when the room has one member (no thread exists), and `THREAD pending` only for rooms of 2+. SKILL.md (Phase 6) must say so. |
| 2026-10-25 | 06 section 1 | `crew.py` exit codes by API error: LINK_REQUIRED, OFFER_EXPIRED, OFFER_STALE, ALREADY_IN_ROOM and EVENT_STARTED give 2; VALIDATION_FAILED, NOT_FOUND and OFFER_CLOSED give 4; RATE_LIMITED, UNAUTHORIZED (after one automatic re-register) and INTERNAL give 5. |
| 2026-10-25 | FR-UPD-01 | `link_required` is reserved but not emitted: the 409 on accept already carries the code synchronously. `room_active` is emitted by the bot once the thread exists (Phase 4). |
| 2026-10-25 | FR-OFR-01 | Accepting a `new_room` offer fails with `EVENT_STARTED` once the student's own window has ended; accepting a `join` offer fails once the room window has started. |
| 2026-10-25 | FR-ROM-04 | `window_changed` fires whenever a join changes the room window, including when it narrows because the joiner's window is shorter, since the existing members' plan did move. |
| 2026-10-25 | 02 section 6 | SQLite connections use `BEGIN IMMEDIATE` so concurrent writers queue on the busy timeout instead of failing on lock upgrade. Every unit of work therefore takes the write lock; acceptable at this scale. |
| 2026-10-25 | FR-INS-04 | The per-IP registration limit uses the socket peer address. Behind a reverse proxy (Phase 5) this must be changed to trust the proxy's `X-Forwarded-For`, or all students share one bucket. |
| 2026-10-25 | 03 section 1 | Only successful responses are stored for `Idempotency-Key` replay. Reusing a key on a different path returns `VALIDATION_FAILED`. |
| 2026-10-25 | FR-INT-04 | Until Phase 3 adds the time budget, matching is synchronous and `POST /v1/intents` always returns an offer (never 202). The route already returns 202 if the matcher returns no offer. |
| 2026-10-25 | 09 section 1 | `matching` sits above `agents` in the import-linter layers. The matcher builds delegates and hosts and runs them, so it must import the agent types; `agents`, `persistence` and `telemetry` stay independent siblings. |
| 2026-10-25 | 04 sections 2-3, P-2 | Counters snap inward to a 15-minute grid. A counter clipped to a student's exact flex bound would store that private value in `negotiation_steps` and `public_events`, which P-2 forbids. The guard still checks against the true flex window. Residual leakage: a counter reveals the bound to within 15 minutes, and a bound that is already on the grid (for example 17:30) can appear exactly. |
| 2026-10-25 | 04 section 4 | A member's own counter window is never stored. Steps for member delegates record the evaluated window and the verdict only; the host's merged counter becomes the next proposal. |
| 2026-10-25 | 04 section 4 | When the joiner accepts a counter that the host proposed, the room confirms the same window before it counts as an agreement (FR-MAT-05). With the deterministic policy the confirmation always passes; it matters once an LLM chooser is added. |
| 2026-10-25 | 04 section 4 | The joiner's fallback opening proposal has length `max(joiner minimum, longest minimum in the room)`, placed as near the room window as the joiner's flex allows. Room minimum is the longest `activity_min_minutes` among current members. |
| 2026-10-25 | FR-MAT-03 | Pre-score is `overlap / joiner window + 0.5 * (vibe match)`; ties go to the larger room, then the older one. |
| 2026-10-25 | FR-INT-04 | The matcher enforces the 10 s budget by not starting another room negotiation once it is spent, then returns the best result so far. If matching raises, the intent stays in `matching`, `POST /v1/intents` returns 202, and the offer sweeper retries stranded intents every 30 s. |
| 2026-10-25 | 02 section 6 | Negotiation runs with no database transaction open. Rooms are snapshotted in a short read, negotiated in memory under per-room locks, and the offer is written in one transaction. The stale check at accept time remains the correctness guarantee; the locks only reduce stale offers. Locks are in-process threading locks, adequate for the single-process deployment. |
| 2026-10-25 | FR-MAT-09 | Public events use the Mission Control vocabulary: `match_requested`, `negotiation_started`, `candidate_proposed`, then `counteroffer_proposed`, `proposal_rejected` or `proposal_confirmed` per step, and `negotiation_failed` with a `failure_code` (`rejected`, `rounds_exhausted`, `no_allowed_window`, `no_common_window`). |
| 2026-10-25 | 05 section 3 | Outbox payloads are the ones Phase 2 writes (`room_id`, `alias`, `discord_user_id` snapshot, `kind` for `post_message` and `dm_user`), not the `template`/`vars` shape in the spec table. Templates are chosen by `kind` inside `discord_bot/messages.py`, so payloads stay plain data. |
| 2026-10-25 | 05 section 3 | A job whose prerequisite is missing (for example `add_member` before the thread exists) fails the attempt and retries on the normal 1-2-4-8-16 s backoff. Jobs are ordered by creation time, so this is rare. A `create_thread` retry never makes a second thread because it checks `rooms.discord_thread_id` first; a crash between creating the thread and recording it could still leave one orphan thread. |
| 2026-10-25 | FR-BOT-04 | If a DM fails with Forbidden the job is marked done and logged. Cubbie students still receive the link through the `room_active` update written when the thread is recorded. A Discord-only student with closed DMs finds the thread in their Discord sidebar. |
| 2026-10-25 | FR-UPD-01 | `room_active` is written by `record_thread` for every non-synthetic member when the thread is created. `joined` and `member_joined` also carry `thread_url` when the thread already exists. |
| 2026-10-25 | FR-BOT-08, FR-BOT-07 | Reminders, mention Q&A and `/crew meetpoint` stay in Phase 7 as the plan says. `/crew meetpoint` replies "coming soon". |
| 2026-10-25 | FR-ROM-03 | The room lifecycle (close at window end + 2 h, archive at + 24 h) is implemented now as `workers/room_lifecycle.py` because it drives the `archive_thread` job. It was not listed in a phase. |
| 2026-10-25 | FR-BOT-06 | Board join: the student's window is the room window clipped to their earliest/latest (times typed as HH:MM on the event's date in `CREWBIE_TIMEZONE`); flex equals earliest/latest. Matching runs against that room only. If it agrees they confirm to join; if not, they are offered a new crew instead. |
| 2026-10-25 | 05 section 2 | Command replies are deferred and ephemeral. Slash commands and the persistent Join button are registered to the guild at startup (`CREWBIE_DISCORD_GUILD_ID`). Welcome messages name members as text and do not ping them. |
| 2026-10-25 | 05 section 1 | New optional variable `CREWBIE_DISCORD_TEST_CHANNEL_ID`, used only by the opt-in `discord_live` test. |
| 2026-10-25 | FR-BOT-05, NFR-REL-01 | Found in the first live run: the bot role is blocked from posting in `#crew-board` by the `@everyone` "Send Messages" deny, so the card job failed with Discord 50013 and stayed failed. Fix: give the bot an explicit allow in that channel (see 08, I-02 step 1). Added `POST /v1/admin/outbox/retry` and a startup reconcile that re-queues a card for every open or active room without one. |
